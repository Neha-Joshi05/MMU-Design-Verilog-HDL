## 🎯 Objective

Design and verify a simplified, parameterizable Memory Management
Unit (MMU) in Verilog that performs virtual-to-physical address
translation using a software-defined page table, with valid-bit
checking and read/write permission enforcement.

---

## 📖 What is an MMU?

**Simple explanation:** A program never directly touches physical
RAM. It works with *virtual addresses*. The MMU is the hardware
translator that converts those virtual addresses into real,
physical memory locations — and blocks illegal accesses.

**Technical explanation:** The MMU splits an incoming virtual
address into a **page number** (upper bits) and an **offset**
(lower bits). It uses the page number to index into a **page
table**, which stores a frame number plus control bits (valid,
read, write). If the page is valid and the access type is
permitted, the MMU concatenates the frame number with the offset
to produce the physical address. Otherwise, it raises a
**page fault** (invalid page) or **protection fault** (illegal
access type).

### Workflow
```
Virtual Address Input
        ↓
Page Number Extraction  +  Offset Extraction
        ↓
Page Table Lookup
        ↓
Valid Bit Check ──── (invalid) ───→ PAGE FAULT
        ↓ (valid)
Permission Check ──── (denied) ───→ PROTECTION FAULT
        ↓ (allowed)
Physical Frame Mapping
        ↓
Physical Address Output
```

## 🏭 Industry Relevance

MMUs are at the heart of every modern CPU and SoC. They enable:

- **Operating systems** — virtual memory, process isolation, swapping
- **Security** — preventing one process from reading another's memory
- **Embedded systems** — Linux/RTOS on ARM/RISC-V cores use hardware MMUs
- **Mobile & server CPUs** — every smartphone and cloud server CPU has one

Companies like **Intel, ARM, Qualcomm, and AMD** all design custom
MMU/TLB micro-architectures as part of their CPU IP — this project
demonstrates the foundational logic behind that hardware.

## 🛠️ Address & Page Table Format

| Field | Width | Description |
|---|---|---|
| Virtual Address | 8 bits | Address generated by "CPU" |
| Physical Address | 8 bits | Real memory address after translation |
| Page Number | 4 bits (VA[7:4]) | Selects which page table entry to use |
| Offset | 4 bits (VA[3:0]) | Byte position within the 16-byte page |

### Page Table Entry (PTE) — 8 bits per entry

| Bits | Field | Meaning |
|---|---|---|
| [7:4] | Frame Number | Physical page this maps to |
| [3]   | Valid bit | 1 = page is mapped, 0 = page fault |
| [2]   | Read permission | 1 = read allowed |
| [1]   | Write permission | 1 = write allowed |
| [0]   | Reserved | For future execute-permission bit |

## 🚀 How to Simulate

### Option A — Local (Icarus Verilog + GTKWave)

```bash
# Install Icarus Verilog (one-time)
# Windows: download from bleyer.org/icarus
# Mac:     brew install icarus-verilog
# Linux:   sudo apt install iverilog gtkwave

# Run the simulation
bash simulation/run_sim.sh        # Linux/Mac
simulation\run_sim.bat            # Windows

# View waveform
gtkwave waveforms/mmu_waveform.vcd
```

### Option B — EDA Playground (no install needed)

1. Go to [edaplayground.com](https://edaplayground.com)
2. Paste `rtl/mmu.v` content into the left "Design" panel
3. Paste `tb/mmu_tb.v` content into the right "Testbench" panel
4. Select **Icarus Verilog 0.10** as the simulator
5. Check **"Open EPWave after run"** to see waveforms in-browser
6. Click **Run**

## 🔬 FPGA Implementation (if hardware available)

1. Create a new Vivado project, add `rtl/mmu.v` and `constraints/mmu.xdc`
2. Run **Synthesis** → check utilization report (LUTs, FFs used)
3. Run **Implementation** → check timing report (no negative slack)
4. **Generate Bitstream** → program the board
5. Use switches for `virtual_addr`, push buttons for `access_read`/`access_write`/`enable`
6. Observe LEDs for `physical_addr`, `page_fault`, `protection_fault`

If no hardware is available, the **simulation waveform + synthesis
report act as proof of correct, synthesizable design** — this is
standard practice in academic and early-career VLSI portfolios.
